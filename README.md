# MiSTer Experimental Core Incubator

An experimental distribution channel for unfinished, first-party, community, and AI-assisted MiSTer FPGA cores.

The goal is deliberately different from replacing the main MiSTer distribution: **give new developers a safe place to publish working experiments, let users opt in, and provide a path for successful projects to graduate.**

## Why this exists

MiSTer already has a mature Downloader ecosystem with support for custom databases and drop-in `.ini` files. This project uses that machinery instead of creating a competing package format.

The important addition is the **incubator workflow**:

`idea → experimental → developing → candidate → graduated`

A core can stay experimental indefinitely, be archived, or graduate into a normal community/mainline distribution when it has demonstrated stability and maintenance.

## Components

### `scripts/update_experimental.sh`

A dedicated launcher intended to be copied to:

```text
/media/fat/Scripts/update_experimental.sh
```

It installs a Downloader drop-in database at:

```text
/media/fat/downloader_experimental.ini
```

and then launches the existing MiSTer Downloader.

The script does **not** replace or edit the user's main `downloader.ini`.

### `metadata/cores.json`

Human-readable incubator metadata. This is intentionally separate from the Downloader database: Downloader handles files; this metadata describes projects, status, source repositories, authors, hardware requirements, and graduation state.

### `db/`

Reserved for the generated custom Downloader database from `DB-Template_MiSTer`.

## Current design

The custom database URL should be generated by the standard MiSTer DB Template workflow. A repository following the template exposes a database at:

```text
https://raw.githubusercontent.com/OWNER/REPO/db/db.json.zip
```

Users can also consume the generated drop-in `.ini` directly. MiSTer's Downloader supports these custom databases and drop-in database files. citeturn504142search2turn625280search4

## Security model

Experimental cores are **untrusted software artifacts**.

This project should avoid per-core install scripts whenever possible. A core submission should consist of files that Downloader places into the MiSTer filesystem plus metadata. Users should not be asked to pipe remote shell code into `sh`.

Remember that MiSTer scripts run with powerful privileges; the official Update All project explicitly warns users to research scripts before executing them. citeturn625280search0

## Proposed submission rules

A submission should provide:

- Source repository
- License
- Core name and platform
- Current development status
- Known limitations
- Required ROM/BIOS files, when applicable
- Whether SDRAM is required
- Hardware compatibility notes
- A reproducible build or release artifact
- A maintainer/contact

AI-assisted code is allowed. It is not automatically rejected, but the submitting developer remains responsible for the resulting core.

## Graduation criteria

A project becomes a **candidate** when it has a reproducible build, documented controls and limitations, basic functional testing, and an identified maintainer.

A candidate can be **graduated** when it is stable enough that normal MiSTer users do not need to treat it as an experiment and the maintainer is prepared to support it outside the incubator.

Graduation is intentionally a human review decision rather than an automatic score.

## The precedent

The idea is not completely unprecedented: `TheJesusFish/Slop-Core` is already a real custom Downloader database containing vibe-coded, MAME-based MiSTer cores. This project aims to turn that kind of one-off effort into a more standardized incubator and updater workflow. citeturn504142search0

## Development roadmap

### Phase 1 — usable MVP

- Custom Downloader database
- `update_experimental.sh`
- `cores.json` metadata schema
- Submission template
- Basic README and safety rules

### Phase 2 — better UX

- Human-friendly list of installed experimental cores
- Per-core enable/disable support via Downloader filters
- Version/status display
- Optional automatic cleanup of archived projects

### Phase 3 — graduation tooling

- Submission review checklist
- Candidate channel
- Graduation records
- Automated validation of metadata and repository structure
